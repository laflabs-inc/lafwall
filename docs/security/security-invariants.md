# Security Invariants

Status: **Accepted baseline**

Accepted: 2026-07-30

These invariants are the highest-priority repository contract. Changing one is
a security-policy change and requires explicit approval plus a documented
security review.

## Cryptography and key custody

1. Cryptographic primitives are provided by established, reviewed libraries.
   Laf Secrets never implements AES, GCM, random generation, hashing, or
   signature primitives itself.
2. Every secret version uses a freshly generated 256-bit data-encryption key
   (DEK).
3. Secret plaintext is encrypted with AES-256-GCM and a unique 96-bit nonce
   generated by a cryptographically secure random source.
4. The authenticated additional data (AAD) has a canonical, versioned
   encoding. It binds at least:
   - tenant ID;
   - project ID;
   - environment ID;
   - logical secret ID;
   - secret version ID and sequence;
   - encryption format version.
5. A DEK is wrapped by a key-encryption key (KEK) through an approved
   `KekProvider`. A plaintext DEK is never persisted.
6. Production KEKs are stored outside the application database and are not
   exportable through Laf Secrets.
7. Ciphertext, nonce, wrapped DEK, KEK reference, AAD format version, and
   algorithm identifiers are persisted. Plaintext and unwrapped DEKs are not.
8. Authentication-tag failure, context mismatch, malformed envelopes, unknown
   algorithms, and key-provider errors fail closed.
9. Key or encryption format changes use explicit versioning and tested
   migrations. Existing ciphertext is never silently reinterpreted.

## Plaintext handling

1. Secret values are accepted and returned only by explicit value operations.
2. Metadata listing, version history, search, audit, errors, metrics, traces,
   and health endpoints never contain plaintext or a reversible derivative.
3. Plaintext lifetime and copies in process memory are minimized. Components
   receive plaintext only when their use case requires it.
4. HTTP responses containing plaintext are non-cacheable and must not be
   included in server, proxy, browser, or observability capture.
5. Secret values are never accepted in URL paths, query strings, CLI process
   arguments, or other routinely recorded channels.

## Authentication and tokens

1. Human identity uses an approved OIDC issuer and immutable `(issuer,
   subject)` identity, not email address.
2. Signature, issuer, audience, expiry, not-before, and allowed-algorithm
   validation is mandatory.
3. Service tokens are high-entropy opaque credentials, shown in plaintext only
   once.
4. The database stores a token identifier, a non-reversible verifier, scopes,
   status, expiry, and operational metadata, never the credential itself.
5. Token verification is constant-time at the secret-comparison boundary.
6. Expired, revoked, malformed, or unknown credentials are denied without
   revealing which validation step failed.

## Authorization and tenant isolation

1. Authorization is deny-by-default.
2. Every use case authorizes the principal, action, tenant, and target resource
   before sensitive work is performed.
3. Resource identifiers alone never confer access.
4. Cross-tenant access is structurally constrained in storage queries and
   covered by negative integration tests.
5. Administrative roles do not implicitly grant access to secret plaintext
   unless the approved permission model says so explicitly.
6. Application and migration database roles follow least privilege.

## Versioning and deletion

1. A secret version is immutable after creation.
2. Updating a secret value creates a new version in a transaction.
3. Version sequence allocation is concurrency-safe and unique within the
   logical secret.
4. Deletion is recoverable by default. Archived or soft-deleted resources are
   inaccessible through normal read and reveal paths.
5. Permanent destruction requires a separate approved policy and audit trail.

## Auditability

1. Security-relevant reads, writes, denied operations, token lifecycle events,
   role changes, and administrative actions produce structured audit events.
2. Successful state changes and their required audit event commit atomically.
3. Audit records contain stable actor, action, resource, tenant, outcome, time,
   request correlation, and safe context fields.
4. Audit records never contain secret values, credentials, raw authorization
   headers, wrapped keys, or sensitive request bodies.
5. Application code cannot update or delete audit events through normal
   runtime permissions.
6. Audit delivery or persistence failure follows an approved fail-closed
   policy for security-sensitive operations.

## Operational safety

1. Production startup fails if a test key provider, insecure default,
   incomplete authentication configuration, or unknown security mode is
   selected.
2. Backups are encrypted and treated as sensitive. Restore tests verify tenant
   isolation and key-provider dependencies.
3. Logs and telemetry use allowlisted fields rather than best-effort
   redaction alone.
4. Rate, size, pagination, and concurrency limits are explicit and fail safely.
5. Readiness does not claim success when required storage or key-provider
   dependencies cannot safely serve requests.
